# SeekAndDestroy — Deployment

Two targets: a laptop, and a single Azure VM running the container stack. What
differs between them is almost entirely **which defaults stop being safe**.

The compose file's defaults are chosen for a laptop: services bound to
loopback, no authentication on Qdrant or Redis, a published JWT signing key,
Grafana open to anonymous viewers. Every one of those is fine when the only
client is you on localhost, and wrong the moment a host is reachable by anyone
else. `docker/.env.example` marks the four that must change.

## 1. Local

**Prerequisites.** SQL Server (Mixed Mode if you intend to use Docker — see
[setup.md § 1a](setup.md)), Python 3.12 venv, Node, and Docker Desktop only if
you want Qdrant or the full container stack.

**Database.** One command creates, schemas, migrates, seeds and creates the
least-privilege login:

```powershell
.\scripts\provision-database.ps1 -Server LAPTOP-R6U8H616
```

**A sign-in password.** There is no default credential anywhere in this
platform — an employee with no password simply cannot sign in. Set one:

```powershell
.venv\Scripts\python.exe scripts\set_password.py E1001
```

It prompts twice, echoes nothing, and stores only an scrypt hash. Sign in at
the UI with that employee number (or the employee's email) and the password
you chose.

**Run natively** (three terminals, or the container stack below):

```powershell
cd ai-service; ..\.venv\Scripts\python.exe -m uvicorn app.main:app --port 8088
cd api-gateway\SeekAndDestroy.Api; dotnet run --urls http://127.0.0.1:5090
cd ui; npm run dev
```

**Optional: persistent vector index.** Without Qdrant the index is rebuilt in
process memory on every start — which, with a real embedding provider
configured, means re-embedding ~2,400 documents through a billed API at each
boot. Qdrant makes that a one-time cost:

```powershell
docker compose -f docker/docker-compose.yml up -d qdrant
# then add to ai-service/.env:
#   SAD_RETRIEVAL__BACKEND=qdrant
```

**Full container stack locally** — including its own SQL Server, so nothing on
the host is touched and there is no Mixed Mode to enable (the image is
SQL-auth only):

```powershell
copy docker\.env.example docker\.env   # fill in SAD_SA_PASSWORD and SAD_DB_PASSWORD
docker compose -f docker/docker-compose.yml --profile core up --build
```

First run takes a few minutes: it pulls SQL Server, builds three images, then
`db-init` creates the database, applies schema + migrations + the 96k-row seed
and creates the least-privilege `sad_app` login. Subsequent runs skip all of
that — `db-init` is guarded on the presence of `sad.Employee`, so `up` is safe
to repeat. To rebuild from scratch, drop the volume:
`docker compose --profile core down -v`.

The UI is then on <http://localhost:8080>. Everything else — gateway,
ai-service, Qdrant, Redis, SQL Server — is bound to loopback and reached
through the UI's nginx proxy.

**Connecting SSMS / Azure Data Studio to the containerised database:**

```
Server:  127.0.0.1,14330        <- NOT localhost,14330
Auth:    SQL Server Authentication
```

Use the IPv4 literal. Docker publishes the port on IPv4 only, while
`localhost` resolves to IPv6 `::1` first on Windows, so `localhost,14330`
hangs and then reports "server is not found or not accessible" — which reads
like the container is broken when it is fine.

Verify the grants are real while you are there: `sad_app` can `SELECT` from
`sad.InfrastructureCluster` but an `UPDATE` returns *"The UPDATE permission
was denied"*. That is the CMDB-is-read-only design enforced by the database
rather than by convention.

## 2. Azure VM

### 2.1 The database

Install SQL Server on the VM (or use Azure SQL), enable **Mixed Mode** — Windows
auth cannot work across a cloud boundary with no shared domain — then:

```powershell
.\scripts\provision-database.ps1 -Server <vm-ip>,1433 -AdminUser <admin>
```

No backup/restore is needed: the seed is deterministic, so schema + seed
reproduces the estate byte for byte from 6.6 MB of SQL. What that does **not**
carry over is investigation and recommendation history — those are governance
records generated by use. If you need them, take a real backup instead.

### 2.2 Secrets — the part that is not optional

```powershell
copy docker\.env.example docker\.env
python -c "import secrets; print(secrets.token_urlsafe(48))"   # signing key
```

Four values must change from their defaults before the host is reachable:

| Variable | Why the default is unsafe |
|---|---|
| `SAD_AUTH_LOCAL_SIGNING_KEY` | Defaults to a literal string published in this repository. Anyone can mint a valid token for any employee — including one that approves recommendations. |
| `SAD_QDRANT_API_KEY` | Qdrant has no authentication at all by default. |
| `SAD_GRAFANA_ANONYMOUS` | Off by default. Setting it to `true` publishes every infrastructure metric to anyone who loads `/grafana/` - it is reachable from the internet, not just from the VM. |
| `SAD_GRAFANA_ADMIN_PASSWORD` | REQUIRED. Compose refuses to start without it. Grafana is served at `/grafana/` on the public origin, so there is no safe default. |

The signing key must be **identical** for ai-service and api-gateway. They
validate each other's tokens; a mismatch fails closed, with 401s that look
like a login bug.

### 2.3 Network

Compose binds every internal service to `127.0.0.1`. Only the UI (`8080`) is
published on all interfaces, and the browser only ever talks to it — nginx
proxies `/api/` to the gateway over the compose network.

So the NSG needs **one** inbound rule: 8080 (or 443 once TLS is terminated).

Do not add 1433, 6333, 6379, 9090 or 3000. If you need SSMS from your laptop,
open 1433 to *your* IP for the migration and close it again, or use Azure
Bastion. Port 1433 open to the internet attracts automated `sa` brute-forcing
within minutes.

### 2.4 Start it

```bash
docker compose -f docker/docker-compose.yml --profile core up -d --build
```

### 2.5 Verify

```bash
curl http://localhost:8088/api/health          # from the VM
curl http://localhost:5090/health              # from the VM
curl http://<vm-ip>:8080                       # from anywhere allowed
```

Then sign in and run one investigation end to end. A green health check only
proves the process started; it does not prove SQL Server is reachable with the
credentials the container was given.

## 3. Known gaps

Deliberately listed rather than hidden:

- **No TLS.** Tokens travel in cleartext. Put a reverse proxy (Caddy, nginx,
  Application Gateway) in front and terminate HTTPS before anything real.
- **`local` auth mode is not an identity provider.** It validates a password
  against `sad.Employee`, with no lockout, no MFA, no password rotation and no
  reset flow. Rate limiting belongs at the edge. For anything beyond a demo,
  switch to `oidc` — Entra ID, Okta — which turns off both local sign-in paths
  entirely and delegates identity to a system built for it.
- **Single replica only.** LangGraph checkpoints go to SQLite on local disk, so
  a graph paused for human review can only be resumed by the process that
  started it. Scaling past one replica breaks approvals in roughly (N-1)/N of
  cases. This does not affect a single VM. It must be solved before AKS or
  OpenShift — see the checkpoint-store discussion in `docs/architecture.md`.
- **No CI.** Tests run locally, on demand.
